# tokenmonitor plugin

Registers the `tokenmonitor-mcp` MCP server with Claude Code, Codex and
Antigravity. `tokenmonitor-mcp` is the local broker that serves OAuth
credentials to the TokenMonitor ESP32 desk monitor and exposes 17 diagnostic
and control tools to the model. The plugin also ships four skills —
`/tokenmonitor:configure`, `/tokenmonitor:settings`, `/tokenmonitor:theme` and
`/tokenmonitor:firmware` (see [Skills](#skills)).

**The plugin is self-contained.** It bundles the server under
[`server/`](./server/) and launches it directly via
`${CLAUDE_PLUGIN_ROOT}/server/tokenmonitor-mcp` — there is no separate
`go install` / `pipx` / `npm` step. **No language toolchain is required:**
with none on your `PATH` the launcher downloads a prebuilt Go binary for your
platform and verifies it against the committed `server/bin/SHA256SUMS`. When
Node or Python is present, that runtime's dependencies (including native
modules) are resolved on first launch into a per-user cache, so they are
built for your host rather than shipped in the plugin. The Go runtime uses
the same verified prebuilt by default and compiles from source only as a
fallback, or first with `go_prefer=source`.

- Server source: bundled here under [`server/`](./server/) — this is the
  canonical home; edit it in place (no generation step).
- Device firmware & the shared wire contract (`compat/`):
  [`fractal-manifold/tokenmonitor`](https://github.com/fractal-manifold/tokenmonitor)

## Install

1. Nothing to install first. The bundled launcher tries the runtimes below in
   order and uses the first that works; if none is on your `PATH` it fetches
   the verified prebuilt Go binary instead:

   | Runtime | Needs on `PATH`            | First-run setup (cached afterwards)              |
   |---------|----------------------------|--------------------------------------------------|
   | JS      | `node` (≥20) + `npm`       | `npm install` (native modules built for the host)|
   | Python  | `python3` (≥3.11) + `uv` (or `pip`/`venv`) | virtualenv + dependency install  |
   | Go      | nothing (prebuilt), or `go` (≥1.25) | verified prebuilt download; `go build` as the fallback, or first with `go_prefer=source` |

   To pin a runtime, write `runtime=js` (or `python`, `go`) to
   `~/.config/tokenmonitor/launcher.conf`. Default order is
   `js → python → go`.

2. No broker configuration is needed. On its first start the broker writes a
   working default `~/.config/tokenmonitor/tokenmonitor.toml`, and each device
   gets its own key when you pair it with `/tokenmonitor:configure` — the
   device's captive portal asks for WiFi only. The same schema is read by all
   three runtimes; a legacy `service.toml` from a `service-go` install is read
   as a fallback.

3. Add this marketplace and install the plugin from your client.

   Claude Code:

   ```text
   /plugin marketplace add fractal-manifold/mcp-marketplace
   /plugin install tokenmonitor@fractalmanifold-mcp-marketplace
   ```

   Codex CLI:

   ```bash
   codex plugin marketplace add fractal-manifold/mcp-marketplace
   codex plugin add tokenmonitor@fractalmanifold-mcp-marketplace
   ```

   Start a new Codex thread after installing or updating so it picks up the
   plugin's skills and MCP tools. The committed `.codex-plugin/plugin.json` is
   generated by the repository's `tmtools.plugin.vendor_contract` release
   helper; installation consumes it but does not generate it in Codex's cache.

   Antigravity CLI:

   ```bash
   agy plugin install https://github.com/fractal-manifold/mcp-marketplace/plugins/tokenmonitor
   ```

   Antigravity imports `gemini-extension.json`, which registers the MCP server
   (under the key `tokenmonitor`), so the 17 tools are available there. Whether
   the bundled skills and the SessionStart hook load depends on the client:
   Claude Code auto-discovers both, Codex is pointed at `skills/` by its
   manifest, and the Antigravity manifest declares neither — the hook does not
   fire there.

The **first** time the server starts it resolves the chosen runtime's
dependencies into `~/.cache/tokenmonitor/<version>/` (one-time,
per version — a fresh `npm install` / venv / prebuilt fetch or `go build`). That run is
slower; subsequent launches are a cache hit. The launcher logs which
runtime it picked to stderr (`tokenmonitor-mcp launcher: using <runtime> (…)`).

Each Codex, Claude Code or Agy CLI/UI connection then creates a renewable
session lease. All connections share exactly one detached broker daemon across
the three runtimes. The daemon is restarted if it crashes and exits shortly
after the final lease disappears; stale leases from killed clients expire
automatically. Runtime state and daemon logs live under
`$XDG_RUNTIME_DIR/tokenmonitor/` when available, otherwise
`$XDG_CACHE_HOME/tokenmonitor/runtime/`.

### Advanced: standalone / PATH mode

If you would rather run a globally-installed binary, the same
`tokenmonitor-mcp` launcher auto-detects
"PATH mode" whenever it is run from outside the plugin and finds a
`tokenmonitor-mcp-go`, `tokenmonitor-mcp-py` or `tokenmonitor-mcp-js` on your `PATH`. There are no
longer published packages for these — build one from the bundled source
(e.g. `make -C server/go install`, which embeds `server/VERSION` and installs
`tokenmonitor-mcp-go` into `~/.local/bin`;
a bare `go build` reports its version as `dev`) and run `sh server/install.sh`,
which copies the `tokenmonitor-mcp` launcher into `~/.local/bin`.

## Tools exposed to the model

The bundled server exposes 17 tools (see
[`server/compat/tool-schemas.json`](./server/compat/tool-schemas.json) for
the authoritative schemas):

| Tool                          | What it does |
|-------------------------------|--------------|
| `tokenmonitor_status`         | Role (leader/follower), last ESP32 request, request count. |
| `tokenmonitor_health`         | Credentials file + signed self-ping + observed traffic — PASS/FAIL per component. |
| `tokenmonitor_recent_logs`    | Tail of the shared daemon log (default 50 lines). |
| `tokenmonitor_firmware_logs`  | Tail the ESP-IDF log stream from the device over USB-CDC. |
| `tokenmonitor_device_logs`    | Tail diagnostic log lines a device uploaded over the air (config-sync channel). |
| `tokenmonitor_provision_hint` | Laptop LAN IPv4s + broker port as URLs — a diagnostic, and the source of the `broker_url` the provisioning tools seed. Firmware 1.0.0+ finds the broker by mDNS; older firmware needs the address pushed at pairing. |
| `tokenmonitor_list_devices`   | List every device in the local registry (active version, pending update, last poll, providers). |
| `tokenmonitor_register_device`| Register a device so its future polls are recognised. |
| `tokenmonitor_set_device_pending` | Stage a pending config (or firmware-manifest) update for a registered device. `broker_url` is a legacy re-point (same broker, new address) sent only to firmware older than 1.0.1: refused for 1.0.1+, held until the next poll while the version is unknown, and dropped (`broker_url_dropped`) if that poll reports 1.0.1+ or no readable version. |
| `tokenmonitor_publish_firmware` | Stage a firmware OTA (.bin URL + SHA-256) for a registered device. |
| `tokenmonitor_revert_firmware`| Stage a rollback to a previously-shipped firmware version. |
| `tokenmonitor_discover_devices` | mDNS scan (`_tmon._tcp.local.`) for devices waiting for initial config. |
| `tokenmonitor_provision`      | Pair or reconfigure a device over the LAN (needs the 6-digit pairing code on its screen). A device the registry does not know is paired only when asked (`enroll: true` for a first pairing; `enroll` has no default). When a PSK is pushed and `broker_url` is omitted, this host's address is seeded and reported as `broker_url_seeded`, so pre-1.0.0 firmware can leave setup. |
| `tokenmonitor_check_updates`  | Poll the public OTA releases repo and stage a pending OTA per matching, out-of-date device. |
| `tokenmonitor_set_wifi`       | Stage a WiFi change for a registered device. Needs `pass` unless the device has reported that it already remembers the SSID; refuses a remembered **open** network, which the device never auto-joins. |
| `tokenmonitor_usb_scan`       | Enumerate TokenMonitor devices on the serial bus, with a match tier per port and, when the firmware reports it, `has_psk` (absent = unknown, never false). **Linux + macOS** (sysfs / `ioreg`); Windows enumeration is not yet implemented. |
| `tokenmonitor_usb_provision`  | Provision or reconfigure a device over the USB cable: WiFi and PSK (plus optional settings) in one payload, independent of the LAN; every field is optional and `enroll` has no default (`enroll: false` = settings / WiFi only). Firmware 1.0.0+ finds the broker by mDNS; when a PSK is pushed to older or unknown firmware with no `broker_url`, the address is seeded if the provision hint has exactly one URL (`broker_url_seeded`); otherwise the tool asks for `broker_url`. |

## Skills

| Skill | What it does |
|-------|--------------|
| `/tokenmonitor:configure` | Pair a new device or reconfigure an existing one, over the LAN (pairing code) or a USB cable — including changing its WiFi without a factory reset. |
| `/tokenmonitor:settings`  | Remotely change any setting the on-device Settings panel exposes (city, brightness, volume, providers, rotation, theme, pet, custom panel, passphrase). |
| `/tokenmonitor:theme`     | Shortcut for switching Day / Night / Auto theme. |
| `/tokenmonitor:firmware`  | Build signed firmware with `make build-prod` and stage it as an OTA — dev channel first (canary on revertible test units), then stable. |

**Legacy firmware.** Units on firmware older than 1.0.1 treat the broker
address differently (≤ 0.12.0 cannot leave "Waiting for setup" without one and
treat it as a pin). The tools gate on the firmware version the device reports;
the authoritative table is "Legacy firmware compatibility" in the monorepo's
`compat/README.md`.

The skills call the tools by their bare names (`tokenmonitor_…`), so they do
not depend on the MCP server key a client registers.

## Migrating from `service-go`

Disable an older `service-go` systemd unit before installing this release. A
pre-existing process does not participate in the singleton lock and can keep
port 8765 occupied; the session supervisor will retry until that legacy process
is stopped.

## Runtime parity

All three implementations expose the same wire protocol and MCP tool
schemas (verified by shared test vectors under `compat/`; the bundle
carries the runtime slice at [`server/compat/`](./server/compat/)). A
device registered by one runtime is readable by the others. If
`tokenmonitor_status` reports a different runtime than expected, check
`~/.config/tokenmonitor/launcher.conf`.

## Editing the server

`server/` is the canonical source — edit it directly, including
`server/VERSION`, the canonical broker version (bumped in place; there is no
monorepo-root copy). The one **vendored** file is
`server/compat/tool-schemas.json`, which is authoritative in the monorepo's
`compat/` and copied here so the standalone-published plugin can start;
`.codex-plugin/plugin.json` is generated from `.claude-plugin/plugin.json` by
the same helper. Keep both in sync from the monorepo:

```bash
cd tools && PYTHONPATH=. python -m tmtools.plugin.vendor_contract          # re-vendor
cd tools && PYTHONPATH=. python -m tmtools.plugin.vendor_contract --check  # verify (CI / pre-commit)
```
